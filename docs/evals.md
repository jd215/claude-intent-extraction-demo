## Additional observations (manual review)

Beyond the grader-flagged misses above, three behaviors are worth noting
for anyone using this pattern in production:

**Multi-valued ambiguity.** When a query lists alternatives ("catamaran or
sailing yacht"), Claude picks the first option and lowers confidence to 0.75
rather than returning null. Defensible but lossy — a stricter implementation
might leave `vessel_type: null` and let the UI surface both options to the user.

**Adjacent-field inference.** Claude occasionally infers fields that weren't
explicitly stated:
- "Romantic getaway for two in Santorini" → `cabins: 1` inferred from "for two"
- "Party yacht in Ibiza" → `vessel_type: "motor"` inferred from "party yacht"
- "A yacht with gym, spa, and helipad in Monaco" → `vibe: "luxury"` inferred from amenities

These are sensible inferences, but they technically violate the system prompt's
"use null for any field not mentioned" rule. Tightening the prompt would
suppress them at the cost of some user-helpful guesses. Worth knowing the
tradeoff exists.

**Inconsistent currency state.** "cheap sailboat bahamas" produced
`budget_currency: "USD"` with `budget_max: null` — a currency without an
amount. The schema doesn't enforce this relationship. In production, either
the prompt should constrain it ("only set `budget_currency` when `budget_max`
is non-null") or the downstream consumer should ignore orphaned currency.
